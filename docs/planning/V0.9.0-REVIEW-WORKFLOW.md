# v0.9.0 Local Scene Review & Approval

## Trust model

Approval is a **human local action**, not a model tool and not an HTTP request.
DSH's loopback trust fence identifies the machine, not the person; it must not be
used as evidence that a human approved content. Therefore:

- no Approve/Revoke API route exists;
- `POST /diagnostic-tutor/api/scene-config` is a 404, not an approval path;
- CLI approval requires an interactive TTY and an explicit `APPROVE` answer;
- non-interactive executions are refused (tested);
- registry and audit files are local, mode `0600`;
- every entry stores a canonical SHA-256 digest; a changed spec/fallback fails
  registry loading;
- warnings must be explicitly acknowledged (`--ack-warnings`) or the entry is
  refused;
- visual errors block approval.

Residual risk: if a human/agent with real shell permission invokes the CLI in a
TTY and types the confirmation, the CLI cannot distinguish that from the human.
That is an OS permission boundary, not something a localhost check can solve.
The production DSH workspace permission should not allow writes into
`DSH_HOME/storages`.

## CLI

```bash
node scripts/scene-review.mjs lint candidate.json
node scripts/scene-review.mjs approve candidate.json --reviewer "name" --note "checked schema, visual, fallback"
node scripts/scene-review.mjs list
node scripts/scene-review.mjs verify
node scripts/scene-review.mjs revoke <scene-id> --reviewer "name"
```

Registry path:

- `DSH_DIAGNOSTIC_TUTOR_SCENE_REGISTRY` if set;
- otherwise `${DSH_HOME:-~/.dsh}/storages/diagnostic-tutor-approved-scenes.json`.

Audit log: same path + `.audit.jsonl`.

An actual local approval was executed during v0.9 research:

- candidate: locally reviewed unit-circle variant
- digest: `2f0c3705c58eec2217c7ffc0f86a4350f31c2d28e41dbefe4d4b0471c743bd32`
- registry entry + audit event written
- non-TTY approval refused
- loader re-verified digest and visual gate.

## Read-only browser Review

[`preview/scene-review/`](../../preview/scene-review/) loads candidate files from
the reviewer's machine and shows:

- validation result;
- visual diagnostics with severity and suggested fix;
- fallback;
- current canonical SHA-256;
- full SceneSpec;
- exact CLI command to approve.

It has **no approve button**, no write request, and no model call.

## Production resolution

1. `GET /scene-config` returns `{enabled, approved:[...]}`; specs come from the
   compiled code-reviewed catalog plus locally approved entries.
2. The client revalidates each candidate and compares the exact canonical
   `{spec, fallback}` against that read-only list.
3. Model write tools require the same approved content + feature flag; a valid
   but unapproved spec is rejected.
4. Revocation removes the entry; the next page load/config fetch falls back to
   the static explanation.
5. Feature flag off always uses fallback, even if the registry contains scenes.
6. Old clients see Unknown Block for `scene`; no storage migration is needed.

Approval permits safe rendering only; it does not prove conceptual correctness.
