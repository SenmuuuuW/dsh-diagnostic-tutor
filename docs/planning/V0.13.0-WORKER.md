# v0.13.0 Candidate Worker

## Architecture

DSH currently exposes no background model-execution service to plugin tools.
v0.13 uses a deliberately separate local worker:

```text
Tutor -> udt_scene_candidate_create (requested)
      -> scene-candidate-worker-daemon (polls local store)
      -> DSH_SCENE_GENERATOR_COMMAND (external, explicitly configured)
      -> recordGeneratedCandidate (schema + visual, needs-review)
      -> human CLI approval (no model authority)
      -> udt_scene_candidate_attach
```

The daemon is a **development queue bridge**, not a production model service.

## Reliability

- candidate status acts as the lock (`requested -> generating`);
- one attempt per candidate per daemon run;
- configurable timeout, default 10 minutes;
- generator exit/output/fallback failures become `failed` with a reason;
- daemon restart cannot duplicate a Candidate;
- no approval, attach, or evidence authority;
- requestHash dedupe prevents duplicate candidate records;
- retry requires explicit operator action, not an infinite loop.

## Real test

Created a candidate request through the real store, configured an adapter
command that supplied a real-model Scene artifact, ran the daemon: it claimed
`requested`, validated, and moved to `needs-review`. It did not approve or attach.

## Limitation

This proves queueing, timeout/failure handling, idempotent claim, validation and
approval separation. It does not prove live production model generation; that
needs a supported DSH background/model API.
